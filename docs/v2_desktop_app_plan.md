# v2 desktop app (Tauri) — draft plan

*Drafted 2026-10-25. First Mac version built the same day in the separate repo
`../sstracker-desktop` (Tauri; reveal engine in Rust with tests, page auto-fill layer,
polling file watcher). Decided: separate repo, Mac first, Win-Loss unchanged for now.
The existing web tracker (`index.html` / `app.js`, served from GitHub Pages) stays
as it is; v2 is a separate product. Not yet verified: windowed UI on screen, Windows
and Linux save locations, a full live run with the app open.*

## Why

The tracker exists to record information the game shows you but not at the moment
you need it. Example that started this: choosing a soul on the rewards screen while
wanting to know whether a Merchant of Steel is still ahead. The game shows the
central nodes on the map, but not on the rewards screen, so the player has to have
written them down. That is grunt work outside the game.

The game already writes the run state to disk as it goes. v2 reads that file and
fills in the tracker for the player, **showing only what the game has already shown
them**.

## Hard rule: no lookahead

The save file holds the whole run map from the first full save (wave sets, boss
variants, minor bosses, minor nodes, offered artifacts, merchant stock), well
before the game reveals it. v2 must never show any of it early. The reveal rules
below are the product; a bug in them turns a tracker into a lookahead tool.
See memory `no-spoiler-features` and `docs/run_save_decoding.md`.

Not in scope, ever: artifact offers, merchant stock, trials not yet offered, any
prediction from the random-number streams, **and the Celestial alcove events**.
`storyEventStates` lists every Celestial event and its map location from the first
full save (e.g. the Garfield box event, Clipped Wings, Titan Dominion), and knowing
them early is a large pathing advantage. At most the app may show an event after the
player has entered the node.

## What it reads

The game's save folder (Mac: `~/Library/Application Support/Shiny Shoe/MonsterTrain2/saves/`).
The live file is `save-regionRun.json`; `.backup` trails it. The game writes it at
events (run start, battle victory, region/branch choice, battle start), not at
every pick, so the app always lags the game by up to one event.

Read-only, one directory, no network. The file contains the player's platform ID
and display name: parse in memory, never store or transmit them.

## Reveal rules (draft)

Each rule says when a field may appear, and the save field that signals it.

| Tracker field | Revealed when | Save signal |
|---|---|---|
| Boss variants, region curses | Run start (the game shows the icon row) | `runState.nodes[2,4,6,8]` `.scenarioIndex`, slot 9 for Lifemother |
| Central nodes (all regions) | After the Astrael battle (first look at the map) | `numBattlesCompleted` ≥ 1; `nodes[i].mapNodes` shared nodes |
| Wave set + minor boss | When the battle starts | `gameSequence` = 1 and the slot at `runState.distance` |
| Minor nodes (left/right pairs) | When the region is entered | `regionRunVisitedRegions`, `nodes[i].chosenBranch` |
| Trial taken | Battle start; read the finished record afterward | `completedBattles[].trialID` (the record). `nodes[i].trialInfo` is NOT a history: it is rewritten as the run goes (slot 7 held `T1Draw` when taken, later `T3Invasion`), and boss slots hold filler. Use `trialInfo.trialEnabled` only for the battle in progress |
| Souls, relics, deck | When picked (appears at next save) | `souls`, `blessings`, `deckState` |
| Upgrades (champion, units) | After the Light Forge / Merchant of Steel | `deckState[].cardModifiers.cardUpgrades` |

Central-node upgrades (confirmed 2026-10-25): the map in the save is **edited in
place** when a region boss is beaten. After Lylith, one central node in each
remaining region's slot was replaced by an `SoulSavior_Upgraded…` version
(`UpgradedSpellUpgradeMerchant` in Maera's boss slot 2, `UpgradedUnitUpgradeMerchant`
in Thaddeus's slot 4, `SoulSavior_RewardNodeUpgradedBlessingOnly`, the upgraded
Herzal's Hoard, in Tivi's slot 5). The start-of-run map has the base nodes, so the
app must re-read the central nodes after every boss, not once.

Choosing a branch picks only the two minor nodes. The central nodes are identical
on both branches (shared first in `mapNodes`); only their rewards (artifact offers)
are rolled per branch.

To confirm before building: exactly when the game shows the boss-variant row and
each region's central nodes; what `trialInfo` on boss slots means (it is filler:
boss fights never have trials).

## Decoding data v2 needs

Small subset of what `extraction/mt2_decode_*` produces: clan, champion, heart,
soul, trial, node and boss-variant names. Generated tables are in
`docs/run_save_reference.md`; the decoders are `extraction/mt2_decode_runs.py`
and `extraction/mt2_decode_map.py`. v2 should ship a compact JSON of GUID → name
generated by the pipeline, not the whole 234-GUID index.

Open: re-generation after a game patch (new GUIDs); save format changes.

## Shared content with the web app

The tracker's facts are in `gamefacts.js` (hand-authored) and `gamedata.js`
(pipeline-generated), plus `champion-art/` and `souls/`. v2 needs the same content
(boss notes, wave sets, soul text, art).

## Repository: separate or same?

Recommendation: **a separate repository**, shared data via a copy step at first.

- Different toolchain (Rust + Tauri, installers, signing) and release cycle; the
  current repo is a no-build static site served from GitHub Pages.
- Keeps the existing app and its history untouched, as requested.
- Downside: the facts (`gamefacts.js` etc.) drift between repos. Options, in order
  of effort: (1) copy the files with a script when they change; (2) a small
  shared data repo/submodule both consume; (3) v2 imports from the pipeline's
  output directly.
- Start with (1). Revisit (2) if the two apps are both kept long-term.
- The extraction pipeline stays in this repo; it is the source of the data files.

## Platforms

1. **Mac first.** The save path is known and verified.
2. **Windows second.** Unknown: save folder location and whether the JSON is
   identical. Needs a copy of a Windows save.
3. **Linux maybe.** Steam/Proton path; same question.

Tauri gives small installers and a narrow permission model (one directory
read). Signing/notarization is needed to avoid Gatekeeper and SmartScreen warnings.

## Architecture sketch

- Rust side: file watcher on the saves folder (event-driven or short poll),
  JSON parse, reveal-rule engine, emits a "visible state" struct.
- UI: the existing tracker's layout, rebuilt as a web UI inside Tauri, read-only
  fields filled from the engine; manual entry kept as an override so a missed
  save event never blocks the player.
- Reveal engine isolated and unit-tested against recorded snapshots (the
  snapshot watcher's `mt2-save-copy/snapshots/` output is the test corpus).

## Milestones

1. Finish the open questions above using more snapshots (full runs, both outcomes).
2. Write the reveal engine as a standalone library with tests on snapshots.
3. Tauri shell, Mac, read-only view of boss variants + central nodes.
4. Wave sets / minor nodes / trials, then relics, souls, upgrades.
5. Manual override and the web app's notes/popovers.
6. Windows check, then packaging and signing.

## Risks

- Reveal timing bugs show information early. Mitigation: tests that assert nothing
  is visible before its signal, using real snapshot sequences.
- Game patches change the save or the GUIDs.
- Platform ID and name in the save: must never be logged or shipped in test data.
- Scope: a tracker with automatic fill must stay at least as good as the manual
  one when the save is missing or stale.
